## 统计定义与限制

- 使用同环境 AISBench 的 StablePerfMetricCalculator 选取稳态区间和请求集合，另从原始时间点计算未四舍五入的均值及 P90/P99。
- 稳态区间从实际最大客户端并发第二次达到时开始，到最后一次处于该最大并发时结束；选取开始时间落在该闭区间内的请求。每组 results JSON 保存区间边界、请求 ID、所选请求数以及处于最大并发的时间占比。
- TPOT = 1000 ×（末 token 时间 − 首 token 时间）/（输出 token 数 − 1），保留选中请求的完整生命周期。
- AISBench 稳态吞吐 = 所选请求完整输出 token 总数 / 稳态区间时长。它不是严格裁剪到该时间窗内的 token 事件吞吐，部分选中请求可能在窗口后结束。
- 这些数据可以重建客户端并发平台期；不能仅靠客户端数据保证服务端每一步 Decode BS 恒定。DSpark 一个流式 chunk 可含多个 token，不能把 chunk 数当作 token 数。
- 不覆写原始 outputs。输出压缩包同时保存原始 run 与单独复制后生成的官方 stable_stage outputs；两者目录明确区分。
- 源数据成功请求全部输出 1024 token。失败请求、服务退出轮次和未完成轮次不参与排名。

## 拓扑与配置

- 新双机：P 为 177.11.26.1，DP1 TP4 PP2；D 为 177.11.27.1 + 177.11.21.1，DP4 TP4 EP16，共 16 张 D NPU。计时请求完整经过 proxy → P → D。辅助预热逐个 D DP 域发送单 token 请求，不计入测量。
- 旧单机：D 为 177.11.27.1，DP2 TP4 EP8，共 8 张 D NPU。原始 run.py 的客户端端点直连 D:31060，因此单独列组，不能伪称为完整 PD 路径测量，也不能只按卡数直接比较新旧加速比。
- 指定容器 cxy-m31-a5-openeuler-40260585905-1；DSpark 7 draft tokens。新双机本快照图捕获上限 512，HCCL_BUFFSIZE=2048。
- K=1024，输入为 16384 / 131072，输出严格 1024，ignore_eos=True，RR=0，通常总请求数为 4×并发。
- 原始 case 名称包含“128K 90%”，纯 D 按用户要求设置前缀目标 100%；不能把这组结果描述为 90% 命中性能。每个 DP 的实际 local/external cache 指标保存在源 result.json 中。16K 新双机 local 命中 98.4375%，其余由 external KV 覆盖；不把 local 指标改写为 100%。

## 高并发问题与未完成项

旧配置的稳态 TPOT 在并发 128、256、392 分别为 24.602、80.117、97.655ms（完整精度见 CSV）。并发 392 时观察到的每 DP 最大 KV 占用约 7.4%，无抢占，因此不能以完整上下文除 KV 容量得到的 392 作为共享前缀场景的硬上限。

服务日志确认图捕获上限为 512。DSpark 7 对应验证批次每请求最多 8 token；总并发 256 均分四个 DP 已达到每 DP 512 token，负载不均即可超过，440 均分对应 880 token。因此已将新一轮图捕获上限提高到 1024 验证。当前只能称为待验证原因，不能声明已经解决；230 并发均分仍低于 512，20ms 档差距还需继续定位。128K 阶段将按用户指定使用 HCCL_BUFFSIZE=1024。

当前已测达标的最高客户端并发为：新双机 16K 的 20ms 档 91（19.917ms，4240.30 token/s），50ms 档 128（24.602ms，4791.68 token/s）。这是已测集合内的达标点，不是硬件最大支持并发；20ms 档按吞吐选择的最佳点仍是并发 64。双机 128K 尚未完成，不能用旧单机数据补充或外推。

后续启动期间发生过其他任务反复占用 NPU、21 机测试容器被外部停止并删除，以及 MC2 初始化错误。21 机 Docker 事件记录先发送 SIGTERM、20 秒后 SIGKILL，随后 destroy；不能将这些轮次计入性能排名。恢复后的模型预热也报 `No available HCCL links found`，双机 rank 间 MC2 链路未建立。最小 16-rank MC2 探测曾通过，但未证明完整模型服务恢复。随后 27 机 SSH 原凭据认证失败，未能进一步定位或完成补测。上述证据不足以将所有失败归为同一个根因。

115/116 两轮曾被客户端误标为 graph 1024；核对发现 docker cp 复制到了多一层 config 目录，容器实际仍运行 graph 512。已按容器脚本及启动日志更正参数，并保留 configuration-correction.json，不能把它们当作 1024 的性能结果。复制流程现已逐字节核对容器配置，并增加实际日志中的图捕获上限检查。随后启动日志确认 1024 生效，但服务在发压前退出，暂无有效 1024 性能数据。
